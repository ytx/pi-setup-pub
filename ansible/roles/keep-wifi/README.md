# keep-wifi

[日本語](README.ja.md)

Brings the Wi-Fi back by itself. Every minute it pings the default gateway;
when that keeps failing it tries harder step by step - reconnect through
NetworkManager, reload the Wi-Fi driver, reboot.

For the Pi's built-in Wi-Fi (the `brcmfmac` driver).

## What counts as a failure

| State | Meaning |
|---|---|
| No default route | the association or the DHCP lease is gone |
| The gateway does not answer a ping | there is a route, but nothing gets through |

A missing default route is counted as a failure, not skipped: it is what a
completely dropped Wi-Fi looks like - the case that most needs recovering -
and skipping it would mean never reaching the recovery steps.

## The steps

1. Check every 60 seconds.
2. 3 failures in a row: reconnect through NetworkManager
   (`nmcli device disconnect` / `connect`).
3. 3 more: reload the Wi-Fi driver (`rmmod` / `modprobe`).
4. 3 more: reboot.

With the defaults, a lasting outage leads to a reboot after about 9-10
minutes. Lower `keep_wifi_max_fails` or `keep_wifi_interval` to act sooner.

```
[OK] <--------------------------------------+
  |                                         |
  | no route, or no ping reply              | reachable again
  v                                         |
[failures +1] -- fewer than 3 ------------->+
  |                                         |
  | 3 reached                               |
  v                                         |
[step 0: nmcli reconnect] ----------------->+
  |                                         |
  | 3 more                                  |
  v                                         |
[step 1: driver reload] ------------------->+
  |                                         |
  | 3 more                                  |
  v                                         |
[step 2: reboot]                            |
                                            |
  back from any step once reachable --------+
```

Without nmcli, or without a Wi-Fi device to find, step 0 is skipped.

## Variables

| Variable | Default | |
|---|---|---|
| `keep_wifi_interval` | `60` | seconds between checks |
| `keep_wifi_max_fails` | `3` | failures in a row before the next step |
| `keep_wifi_disable_powersave` | `true` | turn Wi-Fi power saving off (below) |
| `keep_wifi_interface` | `""` | the Wi-Fi interface to reconnect; empty finds it |
| `keep_wifi_reconnect_sleep` | `15` | seconds to wait after reconnecting |
| `keep_wifi_reload_sleep` | `10` | seconds to wait after reloading the driver |
| `keep_wifi_persist_log` | `true` | keep an event log on the boot partition (below) |
| `keep_wifi_log_path` | `/boot/firmware/keep-wifi.log` | where |
| `keep_wifi_log_max_bytes` | `65536` | past this, the log is cut to its newer half |

## Power saving off

`brcmfmac` turns power saving on by default. A dozing client only gets the
multicast the access point buffered at DTIM beacons, and access points
(mesh ones especially) drop some of it. The result: **mDNS (`.local`) names
resolve only now and then**, and latency jumps.

It is set as a NetworkManager global default in
`/etc/NetworkManager/conf.d/10-wifi-powersave.conf` - not on the connection,
because profiles generated by netplan (`netplan-wlan0-*`) are rewritten when
regenerated:

```ini
[connection]
wifi.powersave = 2    # 0=default 1=leave alone 2=off 3=on
```

It applies from the next time the connection comes up. The role does not
bring the device down and up (that would cut the SSH session); the reboot at
the end of the playbook does it.

```sh
NetworkManager --print-config | grep -A2 '^\[connection\]'   # loaded?
iw wlan0 get power_save                                      # the radio (needs iw)
dmesg | grep brcmf_cfg80211_set_power_mgmt
```

On a host without NetworkManager it changes nothing and prints a warning.

## Event log, with few SD card writes

With the overlay filesystem the journal is in RAM and gone after a reboot, so
an outage cannot be looked into afterwards. With `keep_wifi_persist_log` a
record is kept on the boot partition.

To spare the SD card, **only the edges of an outage are written** - nothing
on a normal check:

| Event | |
|---|---|
| `DOWN` | an outage starts (once per outage), with the reason |
| `ACTION` | a reconnect, a driver reload or a reboot |
| `UP` | recovered, with how long it took |

```
2026-01-23T11:25:19+00:00 up=338s DOWN   no default route
2026-01-23T11:26:20+00:00 up=399s UP     gateway=192.168.1.1 recovered after 61s
```

`up=` is the uptime in seconds. On an overlay device the clock starts from a
saved value that never changes (`/var/lib/systemd/timesync/clock` is on the
read-only layer), so right after boot the date can be months off until NTP
sets it; `up=` keeps the order right.

```sh
cat /boot/firmware/keep-wifi.log
```

## Managing it

```sh
sudo systemctl status keep-wifi.timer
sudo /usr/local/bin/keep-wifi.sh          # run a check now
sudo journalctl -u keep-wifi
```

The gateway comes from `ip route`. The state - `failures step outage-start`
- is kept in `/var/lib/keep-wifi/state` (in RAM on an overlay device: no SD
writes).

## Tested on

Raspberry Pi OS based on Debian 13 (trixie).
